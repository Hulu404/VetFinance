# VetFinance

Сервис для ветклиник (1 адрес, 2–6 врачей, Ветменеджер): сводит данные Ветменеджера и банка, показывает, заработала ли клиника и на чём, строит финмодель на 4 квартала. Веб-кабинет сейчас, Telegram-бот и слой Claude позже.

Источники правды, в порядке приоритета:
1. `docs/api-contract.md`: контракт между backend и frontend.
2. `design/vetfinance-prototip-v6.html`: внешний вид и поведение экранов.
3. `docs/VetFinance_функционал.md`: функции 1–52 с пометками [MVP], [2], [3].
4. Документ «VetFinance: архитектура и план MVP» (в проекте Claude).

## Стек

- Backend: Python 3.13, FastAPI, SQLAlchemy 2 + Alembic, Postgres (Supabase), pytest.
- Frontend: React + TypeScript + Vite, TanStack Query, React Router, без UI-библиотек: стили из `design/tokens.css`.
- Тесты: pytest (backend, engine), Vitest (frontend), Playwright (e2e).

## Правила, которые нельзя нарушать

1. **Все цифры считает движок на backend.** Frontend форматирует и показывает, но не суммирует, не считает проценты и не пересчитывает сценарии. Исключение: сортировка и фильтрация уже полученных строк.
2. **Деньги: целые копейки** (`bigint`, в JSON `int`). Никаких float для денег. Округление в одном месте: `engine/money.py`.
3. **Движок без сети и случайности.** Чистые функции: снимок данных + допущения → результат с разбивкой. Одни и те же входы всегда дают одни и те же цифры.
4. **Каждая цифра отдаётся с разбивкой и источником** (объект `Figure` из контракта), потому что на экране любая сумма раскрывается в подсказку (функция 5).
5. **Мультиарендность:** `clinic_id` в каждой таблице, доступ через RLS. Запросы без клиники запрещены.
6. **Персональные данные:** ФИО владельцев животных не загружаем. Врачей в данных, которые уйдут в ИИ-слой, заменяем кодами.
7. **ИИ в MVP нет.** Функции 4, 7, 29, 31, 39 делаются упрощённо (шаблоны и правила), бот целиком вне MVP. Границы закладываем: движок отдаёт структурированный результат, к которому потом подключится Claude.
8. **Эталонные тесты.** Расчёт без golden-теста в `tests/golden/` не считается готовым.
9. Сообщения интерфейса, названия статей и документация на русском; код, имена переменных и коммиты на английском.

## Известные ошибки прототипа v6 (не копировать)

- Прибыль квартала IV 2026 701 000 ₽ не сходится со строками таблицы (около 630 000 ₽). Прибыль считается тождеством: выручка − переменные − постоянные − налоги и взносы − обязательства и амортизация.
- Подсказка «+10,8% к III кварталу» сравнивает с IV кварталом 2025. Рост считается к предыдущему кварталу.
- В ОПиУ нет строки «обязательства и амортизация», хотя функция 14 её требует.
- Прототип показывает роли («только просмотр»), спецификация говорит «ролей нет». Делаем по спецификации.
- Календарь в прототипе идёт до конца месяца, по спецификации скользящее окно 22 дня.
- Тарифы с филиалами и годовой скидкой в MVP не делаем.

## Порядок работы (этапы MVP)

Один этап — один законченный модуль: backend и frontend вместе, с рабочим экраном. Сначала тонкий сквозной срез (этап 0), дальше по боли владельца: «где деньги» → «заработали ли» → прогноз. Подробные карточки этапов: `docs/stages.md`.

0. Скелет: вход, клиника, деплой, один сквозной показатель от данных до экрана.
1. Данные и Транзакции: Ветменеджер, выписки 1С, ручной ввод, дубли, категории.
2. Рабочий стол: остаток, месяц, советы с «Почему?».
3. Отчёты: ОПиУ, Норма, Склад.
4. Платёжный календарь и Обязательства.
5. Прайс и себестоимость.
6. Финмодель: прогноз, три сценария, допущения, план-факт.
7. Запуск: подписка ЮКасса, журнал с откатом, админка основателя, пилот.

Условия на сейчас: разработчик один, дизайн делает партнёр (агент `designer` оформляет его решения в токены и спецификации и не меняет внешний вид сам), пилотной клиники нет (тесты на синтетических данных), хостинг в РФ отложен.

Этап закрывается, только когда выполнен его критерий готовности (gate) из `docs/stages.md`. Designer и tester идут на шаг впереди: спецификации экранов и эталонные данные этапа N готовы до начала работы разработчиков над этапом N.

## Как работаем параллельно

- Backend сначала публикует эндпоинт в `docs/api-contract.md` и `backend/openapi.json` (пустая реализация с примером ответа), потом реализует.
- Frontend работает против mock-сервера, собранного из контракта (`frontend/src/mocks/`), и переключается на реальный API через `VITE_API_URL`.
- Tester пишет сценарии по контракту и прототипу заранее, не дожидаясь реализации.
- Designer выпускает токены и спецификации экранов раньше, чем frontend начинает их верстать.
