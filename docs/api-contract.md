# Контракт API VetFinance, версия 1 (этапы 1–5)

Владелец: backend-developer. Frontend строит mock-сервер из примеров этого файла. Изменение контракта: правка здесь, затем `backend/openapi.json`, затем запись в `docs/handoff.md`, если изменение ломающее.

## Общие правила

- Базовый путь `/v1`. Аутентификация: Supabase JWT в `Authorization: Bearer`. Клиника определяется по токену, в путях её нет.
- Деньги: целое число **копеек**. Проценты: число с одним знаком после запятой в долях процента, поле называется `*_pct` (`15.0` значит 15,0%). Даты: `YYYY-MM-DD`, время: ISO 8601 с часовым поясом.
- Часовой пояс клиники хранится в `clinic.timezone`. «Сегодня» считает backend и отдаёт в `as_of`.
- Ошибки: `{ "error": { "code": "string", "message": "по-русски", "details": {} } }`. Коды: `unauthorized`, `forbidden`, `not_found`, `validation`, `conflict`, `rate_limited` (HTTP 429, заголовок `Retry-After` в секундах), `sync_failed`.
- Ошибка `validation` (HTTP 422): `details.fields` это объект `{ "имя_поля": "причина" }`, причины: `required`, `invalid`, `must_be_positive`, `too_many_decimals`, `too_large`, `in_future`, `before_opening`, `too_long`, `unknown_field`, `out_of_range`, `out_of_window`, `remaining_gt_principal`, `payment_below_interest` (этап 4), `duplicate_name`, `unknown_item`, `duplicate_item` (этап 5), а для подключений `unreachable` (адрес) и `invalid` (ключ). Если ошибка относится не к полю, а к целому запросу (файл выписки), причина лежит в `details.reason`. Тексты ошибок пользователю показывает клиент по этим кодам, `error.message` предназначен для логов и отладки.
- Списки: `?limit=50&cursor=...`, ответ `{ "items": [], "next_cursor": null }`.

## Объект Figure

Каждый числовой показатель, который можно раскрыть подсказкой, отдаётся так:

```json
{
  "value": 124000000,
  "unit": "rub",
  "breakdown": [
    { "label": "Услуги врачей", "value": 75640000, "unit": "rub" },
    { "label": "Продажа кормов", "value": 32160000, "unit": "rub" }
  ],
  "source": ["vetmanager", "bank"],
  "note": "Данные из Ветменеджера, сверены с эквайрингом и кассой."
}
```

`unit`: `rub` | `pct` | `pp` | `count` | `days`. `source`: массив из `bank`, `vetmanager`, `bot`, `manual`, `calc`. `note` собирает backend по шаблону, клиент его не формирует.

Необязательные поля (с этапа 2; когда не нужны, в ответе их нет):

- `delta: true` у `Figure` и у строки `breakdown`: значение это изменение, а не слагаемое итога. Клиент показывает знак (`+15 400 ₽`, `−3,2%`) и цвет по знаку. Без `delta` положительное число читается как обычное значение.
- `details`: массив `{ "label", "value", "unit" }` справочных строк подсказки. Они не входят в сумму `breakdown` (например, «Средний чек» и «Приёмов» в подсказке выручки). Клиент показывает их под чертой после `breakdown`.
- Для `unit = pct` и `unit = pp` `value` это JSON-число с одним знаком после запятой (`14.8`, `-30.6`), не строка. Для `rub`, `count`, `days` только целое.
- `pp` (с этапа 3): процентные пункты, разница двух процентов (`2.4` читается «2,4 п.п.»). Используется с `delta: true` (`deviation_pp` отчёта «Норма»). В `breakdown` одной Figure могут стоять строки `pct`, `pp` и `rub`.

Правило `source` для остатков (`balance.total`, `balance.bank`, `balance.cash`): объединение `source` операций, вошедших в сумму этой Figure, без повторов, в порядке `bank`, `vetmanager`, `bot`, `manual`. Если во всей Figure нет ни одной вошедшей операции, `source` равен `["manual"]` (остаток из начального остатка, введённого вручную). В остаток входят операции со `status` `ok` и `check`, не входят `duplicate`, операции позже `as_of` и раньше `opening_date` счёта.

### Рабочий стол (функции 1–5) · Этап 2; на этапе 0 только `balance.total` и `balance.bank`

`GET /v1/dashboard?as_of=YYYY-MM-DD` (необязательный параметр `as_of`, по умолчанию «сегодня» в часовом поясе клиники; нужен для сверки с эталонными данными) →

```json
{
  "as_of": "2026-09-09",
  "data_as_of": "2026-09-09T04:12:00+03:00",
  "data_stale": false,
  "balance": {
    "total": Figure, "bank": Figure, "cash": Figure,
    "week_change": Figure | null, "week_change_pct": Figure | null,
    "runway_days": Figure
  },
  "month": {
    "days_passed": 9, "days_total": 30,
    "revenue": Figure, "expenses": Figure, "profit": Figure,
    "profit_margin_pct": Figure, "visits": Figure, "avg_check": Figure
  },
  "balance_trend": [{ "date": "2026-08-27", "value": 50742296 }],
  "balance_trend_info": { "note": "string", "source": ["bank", "vetmanager", "bot", "manual"] },
  "advice": [
    { "id": "cash_runway", "severity": "alert|warning|good", "icon": "🩸", "title": "string", "text": "string",
      "why": { "summary": "string", "steps": ["string"], "sources": ["string"] } }
  ],
  "advice_status": "ready|not_enough_data"
}
```

Все суммы целые копейки, проценты числом с одним знаком. `as_of` вне данных (раньше самого раннего `opening_date` или до первой операции): `200`, нулевые значения, пустой `advice`. Неверный `as_of`: `422 validation`.

**Период и определения** (решение владельца 2026-10-12, правила в `tests/golden/set03/README.md`):

- Всё считается на конец `as_of` включительно: остатки, месяц (с 1-го числа по `as_of`), `days_passed = as_of.day` («9 дней из 30»). Операции дня `as_of` входят и в остаток, и в месяц. В расчёт не входят дубли (`duplicate`), операции позже `as_of` и раньше `opening_date` счёта; переводы между своими счетами не доходы и не расходы; `check` входит.
- `balance.total = bank + cash`; `balance.*.breakdown` по счетам (подпись это название счёта), `source` по правилу остатков (см. «Объект Figure»).
- `balance.week_change` (рубли, `delta: true`): остаток на конец `as_of` минус остаток на конец `as_of − 7` дней. `breakdown`: изменение по каждому счёту (`delta: true`, сумма равна `value`); `details`: «Неделю назад (2 сентября)» и «Сейчас». `balance.week_change_pct` (`unit = pct`, `delta: true`): то же изменение к остатку неделю назад; `breakdown`: «Неделю назад (2 сентября)» и «Сейчас» в рублях. Если `as_of − 7` раньше самого раннего `opening_date`, оба поля равны `null` (ключ есть); `week_change_pct` равен `null` также при остатке неделю назад ≤ 0.
- `balance.runway_days` («Хватит на», `unit = days`): `floor(остаток total × окно ÷ расходы за окно)`, окно 28 дней (меньше, если история короче: дни от самого раннего `opening_date` до `as_of`). Расходы окна: операции `kind = out` без дублей и переводов, `check` входит. Остаток ≤ 0 даёт 0. `breakdown` (по порядку): «Остаток на счетах», «Расходы за N дней», «Расходы в день, в среднем» (рубли), «Окно расчёта» (`days`); в `note` формула с цифрами и фраза, что платежи вперёд не учитываются. Если расходов в окне нет, поля нет (ключа нет в ответе). Целая часть берётся вниз: 17,6 дня показываем как 17.
- `month.revenue`: закрытые счета Ветменеджера (`exec`) с датой в месяце, черновики (`save`) не входят. `breakdown` всегда две строки: «Услуги», «Товары». `details`: «Средний чек» и «Приёмов» (если есть). `source = ["vetmanager"]`.
- `month.expenses`: деньги банка и кассы, операции `kind = out` в месяце; `breakdown` по статьям (без статьи: «Без статьи»), по убыванию суммы, при равенстве по названию. Закупка впрок целиком попадает в расходы месяца закупки: это не ОПиУ (отчёт этапа 3).
- `month.profit = revenue − expenses`, `breakdown`: «Выручка» (+), «Расходы» (−). Это «Прибыль по деньгам» (решение владельца 2026-10-14): вычтены все деньги расходов месяца (оборудование, вывод владельца и платёж по кредиту тоже), налоги, амортизация и комиссия эквайринга не начислены, поэтому число может отличаться от «Чистой прибыли» отчёта «Прибыль и убытки»; это сказано в `note` («Выручка минус все деньги расходов за 1–9 сентября 2026. Налоги, амортизация и комиссия эквайринга здесь не начислены, поэтому число может отличаться от «Чистой прибыли» отчёта.»). В тексте совета `margin_ok` прибыль тоже названа «Прибыль по деньгам».
- `month.profit_margin_pct = прибыль ÷ выручка` (`pct`), `breakdown`: «Прибыль», «Выручка»; при выручке 0 поля нет. `month.visits` (`count`): приёмы месяца, `breakdown` по врачам («Фамилия И.»; при нуле одна строка «Нет приёмов»). `month.avg_check` (`rub`): выручка ÷ число закрытых счетов; `breakdown`: «Выручка» (рубли), «Счетов» (`count`); при отсутствии счетов поля нет.
- `source` производных цифр: объединение источников операций и счетов, из которых получена цифра, в порядке `bank`, `vetmanager`, `bot`, `manual` (без `calc`). Если вошедших данных нет, `["manual"]`.
- `balance_trend`: остаток `total` на конец каждого из 14 дней, оканчивая `as_of`, от старых к новым; дни раньше самого раннего `opening_date` не отдаются (на четвёртый день жизни клиники 4 точки). Последняя точка равна `balance.total.value`. `balance_trend_info`: подсказка точки (`note`, `source`), на каждую точку `Figure` не выдаётся.
- `month.revenue_forecast` и `month.expenses_change_pct` (запрос designer) на этапе 2 не отдаются: нет эталона; клиент работает без них.
- `advice_status` (с 2026-10-14, по запросу frontend): `not_enough_data`, если от самого раннего `opening_date` до `as_of` меньше 7 дней или счетов нет (советы не строились, экран пишет «Пока мало данных»); `ready`, если правила отработали (пустой `advice` тогда значит «отклонений нет»). Клиент не выводит это сам из длины `balance_trend`.
- `advice` всегда есть (может быть пустым), не больше 5 советов, порядок `alert`, `warning`, `good`, внутри по порядку правил. Советов нет, пока данных меньше 7 дней; месячные правила работают с 7-го числа. Правила и пороги (настройки клиники до таблицы `benchmarks`):

| `id` | Условие | `severity` | `icon` |
| --- | --- | --- | --- |
| `cash_runway` | «хватит на» меньше 14 дней / меньше 30 дней | `alert` / `warning` | 🩸 |
| `drug_share` | препараты (статья «Препараты и расходники») больше нормы клиники от выручки (по умолчанию 25%) | `warning` | 💊 |
| `revenue_drop` | выручка месяца меньше 85% выручки тех же первых дней прошлого месяца (если прошлый месяц есть в данных) | `warning` | 📈 |
| `margin_ok` | рентабельность не ниже 12% | `good` | 📈 |
| `cash_gap` (этап 4) | в платёжном календаре есть красные дни; повторяет первое оповещение календаря, поле `link` (см. «Планирование») | `alert` / `warning` | 📅 |

- У каждого совета непустые `why.summary`, `why.steps` (2–5 шагов с числами расчёта), `why.sources`. `id` стабильный. Пределы: `title` до 80 знаков, `text` до 200, шаг до 240. Деньги в текстах как на клиенте («412 800 ₽» с неразрывными пробелами, минус U+2212). В текстах нет слов «ИИ» и «нейросеть», нет фамилий врачей и владельцев животных. Тексты собираются по шаблонам из результата движка (в MVP модели нет), структура `why` та же, что будет у ответа модели.
- Ключи в ответе: `balance.week_change` и `balance.week_change_pct` присутствуют всегда (`null`, если данных нет); `balance.runway_days`, `month.profit_margin_pct`, `month.avg_check` при отсутствии данных не возвращаются (ключа нет).

**Этап 0–1 (история):** ответ содержал только `as_of`, `data_as_of`, `data_stale` (с этапа 1) и `balance` с `total` и `bank`. С этапа 2 все поля выше есть всегда (кроме перечисленных необязательных); `data_as_of` равен времени последней загруженной операции (`created_at`), `null`, если операций нет. `data_stale`: см. «Признак устаревших данных».

Полный пример ответа (эталон №3, `as_of = 2026-09-09`) лежит в `backend/openapi.json` (`components.schemas.DashboardOut.example`).

### Транзакции (функции 6–10) · Этап 1

Статусы операции: `ok` (учитывается), `check` («на проверку»: статьи нет), `duplicate` (не входит в остаток, отчёты и итоги). Остаток исключает только помеченную копию, а не обе операции пары.

```json
Transaction = {
  "id": "b7a1…", "date": "2026-09-09", "description": "Оплата по счёту 12 за аренду, сентябрь",
  "category": { "id": "…", "name": "Аренда" } | null,
  "account": { "id": "…", "name": "Расчётный счёт" },
  "source": "bank|vetmanager|bot|manual",
  "amount": -8500000,
  "kind": "in|out|transfer",
  "status": "ok|check|duplicate",
  "duplicate_state": null | "pending" | "confirmed",
  "duplicate_of": TransactionBrief | null,
  "duplicate_reason": "одинаковая сумма 5 400 ₽, дата 6 сен, разные источники" | null,
  "suggestion": { "category": { "id": "…", "name": "Аренда" }, "reason": "rule|similar",
                  "text": "так же разнесено 3 операции по «ИП Волков»" } | null,
  "figure": {
    "value": -8500000, "unit": "rub",
    "breakdown": [{ "label": "Выписка банка · Расчётный счёт", "value": -8500000, "unit": "rub" }],
    "source": ["bank"],
    "note": "Операция от 9 сентября 2026, счёт «Расчётный счёт». Статья назначена правилом «ИП Волков»."
  }
}
```

- `TransactionBrief` это та же `Transaction` без полей `duplicate_of`, `duplicate_reason` и `suggestion` (вложенность в один уровень).
- `amount`: целые копейки со знаком (`in` положительная, `out` отрицательная, у `transfer` знак своей стороны). Фамилии физических лиц в `description` не хранятся: их вырезает загрузчик, комментарий ручной операции чистится так же.
- `duplicate_state`: у `status = duplicate` значение `pending` (пара не разобрана) или `confirmed` (разобрана, копия осталась в учёте как дубль); у остальных `null`. `duplicate_of` это операция пары, которая остаётся в учёте; для старых данных без пары `null`.
- `suggestion` заполнен только у `status = check` (поиск по правилам и по уже разнесённым операциям того же контрагента, без ИИ). `reason = rule`: статью даёт действующее правило; `reason = similar`: статья, которой чаще всего разнесены операции того же контрагента. Слова «Предлагаем «…»:» добавляет клиент, `text` содержит только продолжение.
- `figure`: `value = amount`, `breakdown` в сумме даёт `value`.

#### `GET /v1/transactions`

Параметры: `tab=all|check|duplicates` (по умолчанию `all`), `from=YYYY-MM-DD`, `to=YYYY-MM-DD`, `limit` (1–200, по умолчанию 50), `cursor`. Ответ `{ "items": [Transaction], "next_cursor": "…" | null }`, порядок: дата от новых к старым, затем стабильный по `id`.

- `all`: все операции, включая `check` и `duplicate`. `check`: только `status = check`. `duplicates`: только неразобранные дубли (`duplicate_state = pending`). Вкладки `check` и `duplicates` без `from/to` возвращают операции за все месяцы; `from/to` применяются, если переданы.
- Неверные `tab`, `from`, `to`, `limit`, `cursor` дают `422 validation`.

#### `GET /v1/transactions/counts`

Счётчики вкладок по всем месяцам: `{ "all": 148, "check": 12, "duplicates": 3 }` (`duplicates` это неразобранные пары). Целые числа без `Figure`: каждое число это длина списка, который открывается рядом.

#### `GET /v1/transactions/summary?month=YYYY-MM`

```json
{ "income": { "value": 29640000, "unit": "rub",
              "breakdown": [{ "label": "Выручка", "value": 16000000, "unit": "rub" }, { "label": "Выручка (эквайринг)", "value": 13640000, "unit": "rub" }],
              "source": ["bank", "vetmanager"], "note": "Доходы за сентябрь 2026: операции со статусами «учтено» и «на проверку», без дублей и переводов между счетами." },
  "expense": { "value": 28100000, "unit": "rub",
               "breakdown": [{ "label": "Аренда", "value": 18000000, "unit": "rub" }, { "label": "Без статьи", "value": 10100000, "unit": "rub" }],
               "source": ["bank", "manual"], "note": "Расходы за сентябрь 2026: …" },
  "balance": { "value": 1540000, "unit": "rub",
               "breakdown": [{ "label": "Доходы", "value": 29640000, "unit": "rub" }, { "label": "Расходы", "value": -28100000, "unit": "rub" }],
               "source": ["bank", "manual"], "note": "Сальдо месяца: доходы минус расходы. Это не остаток на счетах; переводы между своими счетами не входят." } }
```

`balance` это сальдо месяца (доходы минус расходы), не остаток на счетах. В сумму входят операции `kind` `in`/`out` со статусом `ok` и `check` (операции без статьи под подписью «Без статьи»); дубли и переводы исключены; месяц по дате операции. Разбивка `income` и `expense` по статьям, сумма разбивки равна `value`. Если операций нет, `breakdown` содержит одну строку «Нет операций» со значением 0, `source = ["manual"]`. Неверный или отсутствующий `month` даёт `422 validation`.

#### `POST /v1/transactions` (ручная операция)

Тело: `{ "kind": "in|out", "account_id": "…", "category_id": "…" | null, "date": "2026-09-09", "amount": 540000, "comment": "Такси за анализами" | null }`. `amount` положительные копейки, знак ставит `kind`; `comment` до 200 знаков (становится `description`). Ответ `201` и `Transaction` (`source = manual`). Без `category_id` статус `check`; если найдена похожая операция другого источника (тот же счёт, та же сумма со знаком, разница дат не больше 3 дней), статус `duplicate`, `duplicate_state = pending`, в `duplicate_of` её пара. Ошибки `validation` по полям: `account_id`, `date`, `amount`, `kind`: `required`; `amount`: `must_be_positive`, `too_many_decimals`, `too_large` (больше 100 000 000 ₽); `date`: `in_future` (позже «сегодня» клиники), `before_opening` (раньше `opening_date` счёта); `comment`: `too_long`. Счёт или статья другой клиники: `404 not_found`. Операции, внесённые вручную, на этапе 1 не правятся и не удаляются.

#### `PATCH /v1/transactions/{id}`

Тело: `{ "category_id": "…", "create_rule": true }` (`create_rule` по умолчанию `false`). Меняется только статья. Ответ: `Transaction` и поле `rule`:

```json

  "rule": { "id": "…", "match_text": "ИП Волков", "category": { "id": "…", "name": "Аренда" }, "applied_count": 3 } }
```

`rule` равен `null`, если правило не создавали, его нельзя создать (нет ИНН контрагента) или такое правило уже есть.

- Статья сохраняется, статус `check` становится `ok`. `duplicate` остаётся `duplicate`. У переводов статьи нет: `422 validation`, `fields.category_id = "invalid"`.

Оно применяется к уже загруженным операциям без статьи со статусом `check` (того же контрагента и направления) и ко всем новым. Операции с уже назначенной статьёй, в том числе разнесённые вручную, не меняются. `applied_count`: сколько других операций изменило правило.

#### `POST /v1/imports/bank-statement`

`multipart/form-data`: `file` (обязательно, до 10 МБ), `account_id` (необязательно: счёт клиники, для которого выписка; если указан, этот счёт должен быть в файле). Выписка в формате обмена 1С (`1CClientBankExchange`, кодировки windows-1251, cp866, UTF-8). Счета из файла сопоставляются со счетами клиники по номеру (поле `number` счёта задаёт команда). Загрузка выполняется целиком в одной транзакции: либо всё, либо ничего. Повторная загрузка того же файла ничего не создаёт.

```json
{ "import_id": "…", "account": { "id": "…", "name": "Расчётный счёт" },
  "period": { "from": "2026-09-01", "to": "2026-09-22" },

```

### Отчёты (функции 14, 15, 17, 18, 20) · Этап 3

**Состояние:** шаг 2 этапа 3 выполнен: отчёты считает движок (`backend/engine/pnl.py`, `norm.py`, `stock.py`), экспорт формирует Excel и PDF. `backend/openapi.json` содержит примеры (`components.schemas.PnlOut|NormOut|StockOut|StockIdleOut.example`): это настоящие ответы сервиса на эталоне №4 (сентябрь 2026), их собирает `backend/scripts/export_openapi.py`. Формы ответов не меняются без записи в `docs/handoff.md`.

Общее для трёх отчётов:

- Параметры: `month=YYYY-MM` (необязательный; по умолчанию последний закрытый месяц, то есть последний, закончившийся к концу `as_of`), `as_of=YYYY-MM-DD` (необязательный, по умолчанию «сегодня» клиники; для сверки с эталоном и идущего месяца, как у дашборда). Неверный `month`: `422 validation`, `fields.month = "invalid"`; месяц позже месяца `as_of`: `fields.month = "in_future"`. Месяц без данных: `200`, нулевые суммы, `status = empty`.
- Шапка: `month`, `as_of`, `data_as_of` (время последней загруженной операции, `null` без операций), `period`, `status`, `partial_reasons`, `headline`. `period = { "month", "status": "closed|open", "from": "2026-09-01", "to": null | "2026-09-15", "first_month": "2026-07" | null }`. `closed`: `as_of` не раньше последнего дня месяца, `to = null`. `open`: месяц идёт, `to = as_of`; суммы считаются по `as_of` включительно. `first_month`: месяц самой ранней продажи или операции. `data_stale` в отчёты не дублируется, клиент берёт его из `GET /v1/dashboard`.
- `status`: `empty` (нет ни выручки, ни расходов), `partial` (есть причины в `partial_reasons`), `ok`. Причины в таком порядке: `no_vetmanager` (выручка за месяц 0, но другие данные есть), `bank_gap` (выписки покрывают период не целиком: `bank_covered_to` пусто или раньше конца периода, то есть меньшего из конца месяца и `as_of`), `short_period` (месяц идёт, с начала прошло меньше 7 дней), `no_obligations` (нет ни одного начисления обязательств; ОПиУ), `no_benchmark` (для клиники нет норм; «Норма»), у склада `missing_expiry`, `short_history`, `stale_stock`.
- `headline`: вывод одной фразой, собирает backend по шаблону из результата движка (в MVP модели нет). Деньги в тексте как на клиенте (`128 544,93 ₽`, неразрывные пробелы, минус U+2212). Нет слов «ИИ», «катастрофа», «долг». Для `status = empty` поля нет.
- Шаблоны `headline` (текст собирает движок; неразрывные пробелы в суммах): ОПиУ «Клиника заработала 128 544,93 ₽ чистыми: 11,7% выручки, ниже нормы 12–20%.» (слова «в норме», «выше нормы» по границам нормы прибыли), убыток «В августе расходы были больше выручки на 40 000 ₽.», без выручки «В августе выручки нет, расходы 632 000 ₽.», идущий месяц «К 9 сентября клиника заработала 91 600 ₽ чистыми: 17,6% выручки.» (слов о норме нет). «Норма»: «Выше нормы одна статья: препараты и расходники (+29 800 ₽).», «Две статьи выше нормы: … Вместе это 37 800 ₽.», «Ниже нормы одна статья: … Это не всегда плохо, проверьте, нет ли недофинансирования.», «Все статьи в пределах нормы.», справочное списание второй фразой «Отдельно: списание по сроку выше нормы на 13 480 ₽, в расходы месяца оно не входит.» (если выше нормы есть и обычные статьи, добавляется «Вместе со статьями выше нормы это N ₽.»), прибыль ниже нормы «Чистая прибыль ниже нормы на 3,0 п.п.: не хватает 37 200 ₽ до 12% выручки.», идущий месяц «К 9 сентября доли статей посчитаны от выручки за 9 дней. Сравним с нормой, когда месяц закончится.», нет норм «Нормы для вашей клиники пока нет, но доли статей ниже.». «Склад»: «На полке лежат партии с истёкшим сроком на 555 ₽. Их стоит списать. Срок годности истекает у 7 партий на 92 928,50 ₽. Ещё 378 270 ₽ лежат без движения.» (каждая фраза только если есть что сказать).
- Знак: расходные строки приходят положительными (`kind = expense`), «−» ставит клиент по `kind`. Прибыль и убыток со знаком. Слагаемые `breakdown` без знака, кроме строк с `delta` и промежуточных итогов (маржинальная прибыль, чистая прибыль), где вычитаемые идут отрицательными.

Платежи по кредиту (`obligation`), покупка оборудования (`capex`), вывод владельца (`owner_draw`), переводы между счетами и дубли ни в одну строку не входят. Списание по сроку годности отдельной строкой не идёт (деньги ушли закупкой), оно справочно в «Норме» и на «Складе».
- `share_pct` каждой строки: `Figure(pct)`, `breakdown` «Сумма строки», «Выручка» (рубли), `note` «632 000 ÷ 1 240 000». Без выручки поля нет. `net_profit.amount.details`: границы нормы чистой прибыли (`pct`).
- `unclassified`: сумма операций без статьи, они уже внутри `fixed`; `unclassified_count` число таких операций (целое, не `Figure`).
- Идущий месяц (`period.status = open`): выручка, оплаты картой и операции по `as_of`; обязательства и амортизация за весь месяц; налоги только уже уплаченные. Это сказано в `note` строк. Рабочий стол остаётся кассовым («по деньгам»), его «Прибыль» может отличаться от чистой прибыли отчёта.
- `view=direction` добавляет к тем же `rows`:

```json
{ "directions": [
    { "direction": "services", "label": "Услуги", "revenue": Figure, "revenue_share_pct": Figure,
      "direct_costs": Figure, "margin": Figure, "margin_pct": Figure },
    { "direction": "goods", "label": "Товары", "…": "…" } ],
  "common_variable": Figure }
```

  Мост до копейки: `revenue(services) + revenue(goods) = revenue`; `direct_costs(services) + direct_costs(goods) + common_variable = variable`; `margin(services) + margin(goods) − common_variable = marginal_profit`; `margin = revenue − direct_costs`. Прямые расходы направления задаёт поле статьи `direction` (`GET /v1/categories`): проценты врачам и лаборатории → `services`; закупка препаратов, товары для перепродажи → `goods`; комиссия эквайринга и статьи без `direction` → `common_variable`. Постоянные расходы к направлениям не относятся (функция 19 [2]). Маржа товаров занижена, услуг завышена: препараты, израсходованные на приёмах, попадают в товары (решение владельца). Выручка товаров это строки счетов с видом «товар», услуг «услуга».

#### `GET /v1/reports/norm?month=YYYY-MM` (функция 15)

```json
{ "month": "2026-09", "as_of": "2026-10-01", "data_as_of": "…", "period": { "…": "…" }, "status": "ok", "partial_reasons": [],
  "headline": "Выше нормы: аренда и коммуналка (+1 594,79 ₽), списание по сроку (+21 114,75 ₽). Чистая прибыль ниже нормы на 0,3 п.п.",
  "items": [ {
    "key": "rent", "label": "Аренда и коммуналка", "kind": "expense", "memo": false,
    "status": "above", "tone": "bad",
    "norm": { "min_pct": 5.0, "max_pct": 10.0, "source": "industry",
              "breakdown": [ { "label": "Нижняя граница, 5,0%", "value": 5490781, "unit": "rub" }, { "label": "Верхняя граница, 10,0%", "value": 10981561, "unit": "rub" } ],
              "note": "Норма отрасли для ветклиник на 2–6 врачей." },
    "actual_pct": Figure, "deviation_pp": Figure, "deviation_rub": Figure } ] }
```

- Строки в порядке `benchmarks.sort`: ФОТ врачей (`payroll`), Препараты и расходники (`drugs`), Аренда и коммуналка (`rent`), Лаборатории (`lab`), Списание по сроку (`writeoff`, `memo = true`), Эквайринг (`acquiring`), Маркетинг (`marketing`), затем «Остальные статьи» (`other`) и «Чистая прибыль» (`net_profit`). `kind`: `expense`, `other`, `profit`.
- `actual_pct` (`pct`): `breakdown` это статьи, из которых составлена доля, в рублях (сумма равна числителю), `details` «Выручка месяца», `note` «339 800 ÷ 1 240 000 = 27,4%». Сумма всех строк без `memo` (группы + `other` + чистая прибыль) равна выручке до копейки. «ФОТ врачей» = проценты врачам (переменная) + оклады врачей (постоянная); «Препараты и расходники» = закупка препаратов + расходные материалы. Принадлежность статьи строке задаёт поле статьи `norm_key` (`GET /v1/categories`). «Остальные статьи» это всё, на что нет нормы (корма, оклады персонала, прочие, «Без статьи», налоги, обязательства и амортизация).
- Статус: `above` при `сумма × 1000 > max_tenths × выручка`, `below` при `< min_tenths × выручка`, иначе `ok`; границы в целых десятых процента; `no_norm` без нормы. `tone`: расходы `ok → good`, `above → bad`, `below → warn`; чистая прибыль `ok → good`, `above → good`, `below → bad`; `no_norm → neutral`.
- `deviation_pp` (`unit = pp`, `delta`): `actual − граница` от неокруглённых значений, одна цифра; `deviation_rub` (`rub`, `delta`): `сумма − round(выручка × граница / 100)`, плюс над верхней границей, минус под нижней. У `ok` оба равны 0, у `deviation_rub` `breakdown` пуст, в `details` запас до границы: «Запас до верхней границы» у расходов, «Запас до нижней границы» у чистой прибыли. `breakdown` отклонения в рублях: «Ваш расход» и «Граница нормы, N%» (отрицательной), в сумме это отклонение. Показанная доля минус показанная граница равна показанному отклонению в пределах 0,1 п.п.
- `norm`: `min_pct` и `max_pct` (любой может быть `null`), `source` (`industry`: таблица `benchmarks`; `clinic`: норма, заданная у статьи клиники и сильнее отраслевой), `breakdown` границы в рублях при выручке месяца, `note`. Для `no_norm` поля `norm`, `deviation_pp`, `deviation_rub` отсутствуют. `norm.note` отраслевой нормы говорит, что это оценка по прототипу, которую заменят данными отраслевых опросов. Нет норм для клиники (число врачей вне 2–6 и нет собственных): все строки `no_norm`, `partial_reasons = ["no_benchmark"]`.
- Идущий месяц (`period.status = open`): доли считаются, но норма не оценивается (при денежном методе структура неполного месяца искажена): в `items[]` нет ключей `status`, `tone`, `deviation_pp`, `deviation_rub`; `norm` (границы) остаётся. Вывод `headline`: «К 9 сентября доли статей посчитаны от выручки за 9 дней. Сравним с нормой, когда месяц закончится.»
- `writeoff` (`memo`) считается по списаниям месяца с причиной «истёк срок годности» и в сумму 100% не входит.

#### `GET /v1/reports/stock?as_of=&month=` (функция 17)

Остатки и сроки это срез на `as_of`; `month` необязательный и относится только к `written_off_*` (по умолчанию последний закрытый месяц). Ответ содержит `as_of`, `data_as_of`, `month`, `status`, `partial_reasons`, `headline` и поля:

| Поле | Тип | Что это |
| --- | --- | --- |
| `stock_value` | Figure(rub) | остаток склада по закупочной цене, `details` «Позиций» |

- «Без движения»: остаток больше нуля и `idle_days = as_of − last_movement_on ≥ 60` (движение это продажа или списание на приём). Интервалы 60–89, 90–179, от 180 дней; `frozen` их сумма. Позиция с нулевым остатком не входит. Стоимость партии `qty × закупочная цена`.
- Срок годности: партия с остатком и `0 ≤ expires_on − as_of ≤ 60` (60 и сегодняшний день входят). Просроченные (`expires_on < as_of`) идут в `expired_on_hand` и `expired_items`.
- Оборачиваемость `turnover_days = round(стоимость склада × 90 ÷ расход за последние 90 дней)` (окно `as_of − 89 … as_of`; расход по закупочной цене: продажи и использование на приёме), до ближайшего дня. Метод оценки остатка (по закупочной цене партии) сказан в `note`.
- Списания месяца `month` берутся на дату не позже `as_of`.
- Данных склада нет (загрузчик Ветменеджера склад не читает, пока не будет тестового аккаунта; на этапе 3 склад заполняется сидом): `status = empty`, суммы нулевые, списки пусты, `headline` нет. Без расхода за 90 дней `turnover_days.value = 0` (в `note` сказано, что оборачиваемость не посчитать). Без выручки месяца или нормы `written_off_norm.value = 0`, `breakdown` пуст. Статус склада сейчас `ok` или `empty`; причины `missing_expiry`, `short_history`, `stale_stock` не выдаются, пока для них нет эталона. `month` по умолчанию это последний месяц, закончившийся к концу `as_of` (при `as_of` 30 сентября это сентябрь).
- Зарезервированные поля, которых в ответе нет, пока для них нет эталона (правило 8): `expiring[].at_risk` (`{qty, amount: Figure}`, риск списания по расходу за 90 дней), `expiring_at_risk` (Figure(rub)), `missing_expiry_count` (партии без срока). Фолбэки экрана: колонка «Успеем израсходовать?» скрыта, подстрока «4 партии» без суммы риска.

Деньги в Excel числом в рублях с копейками, проценты числом в процентных единицах (`11.7`). В PDF суммы как `1 234 567,89`.

Сильнее всего «X»: −21,0%.») либо «Все услуги с техкартой приносят прибыль. Меньше всего у «X»: 14,0%.», затем при `no_recipe > 0` «У K услуг нет техкарты, поэтому их маржу мы не считаем.»; без единой техкарты «Техкарт пока нет, поэтому маржу мы не считаем. Начните с самых частых услуг: для каждой нужен список материалов и время.» Без услуг ключа `headline` нет, `items = []`, `counts` нули.
- `limit` 1–200; неверные `sort`, `order`, `filter`, `cursor`: `422 invalid`; `limit`: `must_be_positive` или `too_large`.

#### `POST /v1/services`, `PATCH /v1/services/{id}`, `DELETE /v1/services/{id}` (ручные услуги)

`POST` тело `{ "name": "Груминг: стрижка", "group": "Груминг", "price": 180000 }` (`group` необязателен) → `201` и элемент списка (`status = no_recipe`, `source = manual`, `visits_month = 0`, `margin_pct = null`). `PATCH` любое подмножество `name`, `group`, `price` → `204` без тела. `DELETE` → `204`: услуга и её техкарта исчезают из прайса, продажи в Ветменеджере не меняются. Менять и удалять можно только `source = manual`: услуга из Ветменеджера даёт `403 forbidden`, чужая или неизвестная `404 not_found`. Ошибки `422 validation`: `name` (`required`, `too_long` > 120, `duplicate_name`: такое название уже есть без учёта регистра, пробелов и `ё`), `group` (`too_long` > 80), `price` в копейках (`required`, `invalid` не целое, `must_be_positive`, `too_large` > 100 000 000 ₽), `unknown_field`. Цена ручной услуги правится, пока по ней нет продаж; когда продажи появляются, цена берётся из них. Изменения видны в списке сразу.

#### `GET /v1/services/{id}/cost?as_of=`

```json
{ "service": { "id": "…", "name": "Кастрация кота", "group": "Хирургия", "unit_label": "раз", "source": "vetmanager", "price_source": "sales|manual" },
  "status": "ok|no_recipe|partial", "missing": [ "recipe|hour_cost|item_no_cost" ], "basis_month": "2026-09",
  "minutes": 60, "minutes_source": "own|clinic_average",
  "price": Figure, "net_profit": Figure | null, "net_margin_pct": Figure | null,
  "parts": [ { "key": "doctor_pay|drugs|anesthesia|supplies|acquiring|fixed|taxes", "label": "ЗП врача", "amount": Figure | null, "share_pct": Figure | null } ],
  "visits_month": Figure, "monthly_profit": Figure | null }
```

- `parts` всегда семь, в порядке `doctor_pay, drugs, anesthesia, supplies, acquiring, fixed, taxes`. **Тождество:** `price = Σ parts.amount + net_profit` до копейки (пустая часть считается нулём, `net_profit` считается на известных частях); `Σ parts.share_pct + net_margin_pct = 100,0` (доли методом наибольшего остатка, при равенстве более ранняя часть). `price.breakdown` это те же строки (части с ненулевой суммой и «Чистая прибыль»), `note` пишет тождество словами. `net_profit.breakdown`: «Цена» и части со знаком «−». У убыточной услуги прибыль и доля отрицательные, `net_profit.note` называет, сколько не хватает до нуля.
- Расходы услуги не зависят от месяца оказания: техкарта, цены склада, доли и стоимость часа последнего закрытого месяца (`basis_month`).
- `doctor_pay`: процент услуги, иначе средний по клинике (проценты врачам ÷ выручка услуг месяца), `note` называет, откуда процент. `drugs`, `anesthesia`, `supplies`: `breakdown` строка на позицию техкарты («Цефтриаксон, 1 фл. × 140 ₽»), `round(количество × цена позиции)`; цена позиции берётся точная (дробные копейки), `details` называет позиции без цены закупки. `acquiring`, `taxes`: доли выручки закрытого месяца (комиссия и налоги ОПиУ ÷ выручка). `fixed`: `round(стоимость часа × minutes ÷ 60)` от стоимости часа, как она показана (округлённой); `details`: «Стоимость часа», «Время услуги, мин».
- `minutes`: время, использованное в `fixed`: своё из техкарты (`minutes_source = own`) или средняя длительность приёма клиники (`clinic_average`; `note` части `fixed` говорит «Длительность средняя по клинике: 30 мин»).
- `status`: `no_recipe` (техкарты нет; пустая техкарта это `ok` с нулевыми материалами); `partial` (`missing` не пуст); иначе `ok`. `missing` в порядке `recipe`, `hour_cost` (нет стоимости часа: нет часов приёма или расходов месяца, `fixed = null`), `item_no_cost` (у позиции техкарты нет цены закупки, позиция не входит в сумму), `no_expenses` (в ОПиУ базового месяца нет расходов: нет выписки банка и начислений; решение владельца 14: прайс не считаем). При `no_expenses` (рядом всегда и `hour_cost`): `acquiring`, `taxes`, `fixed` и `doctor_pay` по среднему проценту равны `null` (пустой ОПиУ не подставляется нулями), `net_profit`, `net_margin_pct`, `monthly_profit` равны `null`, `status = partial` (или `no_recipe`, если нет техкарты), `price.breakdown` одна строка источника цены; известные части (материалы техкарты, `doctor_pay` с процентом услуги) отдаются, их `share_pct` простая доля цены. В списке у всех услуг `margin_pct` и `monthly_profit` равны `null`, `counts.loss = 0`, `headline` «Нет данных о расходах за сентябрь: прибыль услуг не считаем. Загрузите выписку банка.» При `no_recipe`: `drugs`, `anesthesia`, `supplies` равны `null`; `net_profit`, `net_margin_pct`, `monthly_profit` равны `null` (прибыль без материалов завышена); `price.breakdown` одна строка источника цены; части с известной суммой (`doctor_pay`, `acquiring`, `fixed`, `taxes`) отдаются, их `share_pct` это просто доля цены, сумма 100 не требуется.
- `monthly_profit = net_profit × visits_month` (`details`: «Чистая прибыль одной услуги», «Оказана за сентябрь»).
- Неизвестная или чужая услуга: `404 not_found`.

Чужая или неизвестная услуга: `404` (раньше проверки тела).

#### `GET /v1/calendar?days=22&as_of=YYYY-MM-DD&preview=<suggestion_id>`

`days` в MVP всегда 22 (другое значение: `422`, `fields.days = "invalid"`). `as_of` необязательный (по умолчанию «сегодня» клиники; нужен для эталона), неверный: `422`, `fields.as_of = "invalid"`; `as_of` раньше данных: `200`, тождества дней соблюдены. `preview` необязательный; неизвестный или не относящийся к этому `as_of`: `422`, `fields.preview = "invalid"`. Лишние параметры (`clinic_id`) игнорируются, клиника определяется по токену.

```json
{
  "as_of": "2026-10-07", "data_as_of": "2026-10-07T04:12:00+03:00",
  "window": { "from": "2026-10-07", "to": "2026-10-28" },
  "status": "ok", "partial_reasons": [], "history_days": 189,
  "start_balance": Figure, "safe_balance": Figure, "safe_balance_set": true,
  "preview": null,
  "summary": { "income": Figure, "expense": Figure, "payments_count": 14,
               "lowest": { "date": "2026-10-09", "balance": Figure, "status": "below_safe" } },
  "alerts": [ CalendarAlert ],
  "days": [ CalendarDay ]
}
```

- **Окно** (решение владельца, не `as_of + 1`): 22 календарных дня подряд, первый день `as_of`, последний `as_of + 21`, через границу месяца. `window = { from, to }` ровно с двумя ключами (так требует контрактный тест; число дней всегда 22 и равно длине `days`).
- **Шапка:** `as_of`, `data_as_of` (время последней загруженной операции, `null` без операций), `status`: `empty` (нет счетов или ни одной операции), `partial` (есть причины), `ok`. `partial_reasons` в порядке: `short_history` (в истории меньше трёх полных месяцев перед месяцем `as_of` или `history_days < 85`: `history_days` считает и день `as_of`, а профиль выручки берёт 84 дня до него), `obligations_missing` (в выписке за 90 дней есть платежи статьи типа «обязательство», а в «Обязательствах» ничего нет), `no_bank` (выписок нет). `history_days` (целое, не `Figure`): дней от самой ранней операции банка до `as_of` включительно, `0` без выписок.
- **Остаток на утро:** `days[0].opening` с разбивкой по счетам равен `balance.total` Рабочего стола с тем же `as_of`. `start_balance` оставлен как **алиас** (та же `Figure`, нужен для совместимости; отдельной точки старта на экране нет). Операции дня `as_of`, если они уже есть в выписке, входят в остаток, прошедшие платежи этого дня не прогнозируются, прогноз выручки дня `as_of` уменьшается на поступления этого дня, уже стоящие в выписке (не ниже нуля).
- **Безопасный запас:** `safe_balance` (breakdown одна строка «Задан в настройках», `source = ["manual"]`) это `clinic.safe_balance`; `safe_balance_set = safe_balance.value > 0` (0 значит «не задан»: красные дни только ниже нуля). Меняется через `PATCH /v1/clinic`, отдельного эндпоинта нет.
- **`CalendarDay`:** `{ date, weekday, opening: Figure, income_forecast: Figure, payments: [CalendarPayment], closing: Figure, status: "ok|below_safe|below_zero", note }`. `closing = opening + income_forecast − Σ payments`, `opening` следующего дня равен `closing` предыдущего. Порядок внутри дня: платежи по убыванию суммы (при равенстве по названию), выручка дня в конце. `status`: `below_zero`, если какой-то `balance_after < 0` или `closing < 0`; иначе `below_safe`, если `closing < safe_balance` (ровно запас не красный); иначе `ok`. Красный день это `below_safe` и `below_zero`; экран подписывает оба «ниже запаса». `note`: вывод под разбором дня по шаблону движка («Запас соблюдён: остаток выше 150 000 ₽.», «Остаток на вечер ниже безопасного запаса на 76 663,82 ₽.»). `opening.breakdown`: у первого дня остаток по счетам, у остальных одна строка «Остаток на вечер <дата>». `closing.breakdown`: «На утро», по строке на каждый платёж (со знаком «−», в порядке `payments`), «Выручка, прогноз» (сумма равна `value`). `income_forecast`: `breakdown` одна строка «Среднее поступление по средам», `details` «Таких дней за 12 недель» (`count`) и «Поступило в эти дни», `note` «сумма ÷ число = среднее».
- **`CalendarPayment`:** `{ id, name, category: {id,name}|null, counterparty: {id,name}|null, amount: Figure, source: "recurring|obligation|manual", balance_after: Figure, max_deferral_days, moved_from? }`. `id` непрозрачная строка, одинаковая при тех же данных и `as_of` (у ручного это `id` из `POST /v1/calendar/payments`). `balance_after`: остаток после этого платежа, `breakdown` «До платежа» и платёж со знаком «−»; выручка дня не входит. `name` у регулярного это название контрагента, у обязательства его название. `counterparty` только у `recurring` (иначе `null`); `counterparty.id` непрозрачный (ИНН, а у серии без ИНН ключ из названия), есть всегда. `max_deferral_days`: на сколько дней платёж можно отложить (у регулярного это отсрочка контрагента, у ручного своя, у обязательств 0). `amount.details` у регулярного: три последние суммы по месяцам («Июль», «Август», «Сентябрь»), у кредита «Проценты за <месяц>» и «Основной долг». `moved_from` есть только в ответе с `preview`.
- **`summary`:** `income` (breakdown по календарным неделям Пн–Вс, обрезанным окном: «7–11 октября», «12–18 октября»…; сумма равна `value`), `expense` (то же по неделям; `details`: «Регулярные платежи», «Обязательства», «Внесено вручную»), `payments_count` (целое), `lowest = { date, balance, status }`: день с наименьшим `closing`, при равенстве более ранний; `balance` это `closing` этого дня.
- **Прогноз выручки:** для дня недели среднее поступлений по этому дню недели за 12 полных недель перед `as_of`, только поступления со статьёй типа «доход» (переводы, дубли, «на проверку», возвраты поставщиков и кредиты не входят); истории короче 84 дней: делитель это число таких дней в истории. Копейки через `engine/money.py`.
- **Регулярные платежи** (функция 22): тот же ИНН (без ИНН название) и статья в каждом из 3 последних полных месяцев с одинаковым числом платежей в месяц; день слота это мода за полгода со сдвигом с выходных (налоги вперёд, остальное назад; рабочие дни пн–пт, праздников нет); сумма это медиана трёх последних, разброс до 25%; уже оплаченное в этом месяце не прогнозируется. Статьи типа `obligation`, `capex`, `owner_draw` не прогнозируются. Кредит и лизинг приходят из «Обязательств» (`source = obligation`, выходной переносится на предыдущий рабочий день).
- **`CalendarAlert`:** `{ id, date, date_to, severity: "alert|warning", icon: "📅", title, text, shortfall: Figure, suggestion: MoveSuggestion|null, why: { summary, steps[2..5], sources } }`. Одно оповещение на серию красных дней подряд, по дате, не больше 3. `date` первый красный день, `date_to` последний (у tester в эталоне `end_date`; в API `date_to`). `severity = alert`, если в серии есть `below_zero` (`shortfall` = насколько остаток уходит ниже нуля в худшей точке; breakdown «К выплате…» и «Будет на утро»), иначе `warning` (`shortfall = safe_balance − наименьший closing серии`; breakdown «Безопасный запас» и «Остаток на вечер <дата>» со знаком «−»). `text` не содержит предложения переноса: клиент ставит после него `suggestion.text`. Пределы и запреты как у советов Рабочего стола (`title` до 80, `text` до 200, шаг до 240, деньги как на клиенте, нет слов «ИИ», «катастрофа»).
- **`MoveSuggestion`:** `{ id, payment_id, payment_name, amount: Figure, from_date, to_date, delay_days, closes_gap, lowest_after: Figure, text }` (имена designer; тест tester принимает и их, и вложенный `move`). Перебор: перенос **одного** платежа окна на рабочий день, не позже конца окна и не дальше `max_deferral_days` платежа (по умолчанию 0: такой платёж не переносится). Перенос закрывает разрыв (`closes_gap = true`), если после него все дни серии не ниже запаса и ни один день окна, бывший не красным, не стал красным. Выбор: из закрывающих наименьший сдвиг, затем меньшая сумма, затем более ранняя дата, затем название. Если закрывающего нет: лучший частичный (`closes_gap = false`, текст «Перенос платежа … уменьшит разрыв, но не закроет его.»); если ни один перенос не поднимает минимум серии: `suggestion = null`, и `text` оповещения заканчивается «Перенос одного платежа разрыв не закрывает. Если поставщик согласен подождать, укажите отсрочку у его платежа.» `lowest_after`: самый низкий `closing` окна после переноса (breakdown одна строка «Остаток на вечер <дата>»). Шаблон полного: «Перенесите платёж ООО «Зоовет» на 108 500 ₽ с 7 октября на 12 октября: разрыва не будет.»
- **`?preview=<suggestion_id>`:** тот же календарь, в котором платёж перенесён (`payments[].moved_from` у перенесённого, `preview = { suggestion_id, payment_id, from_date, to_date }`); без `preview` поле равно `null`. Кнопки «Перенести» нет: календарь платежами не управляет.

#### Ручные платежи (разовые)

`POST /v1/calendar/payments` тело `{ "name": "…", "amount": 4500000, "date": "2026-10-14", "category_id": null, "max_deferral_days": 0 }` (`category_id` и `max_deferral_days` необязательны, отсрочка по умолчанию 0) → `201` и `{ id, date, name, category, amount: Figure, source: "manual", max_deferral_days }`. Ошибки `422 validation` (`details.fields`): `name` (`required`, `too_long` > 80), `amount` (`required`, `must_be_positive`, `too_large`, `invalid`), `date` (`required`, `invalid`, `out_of_window`: вне окна календаря на сегодня клиники), `category_id` (`invalid`), `max_deferral_days` (`invalid`, `out_of_range` 0–30), `unknown_field`. `out_of_window` на заглушке не проверяется. `DELETE /v1/calendar/payments/{id}` → `204`; платёж не ручной, чужой или неизвестный: `404 not_found`. Повторов нет; скрыть найденный сервисом регулярный платёж нельзя.

#### `PATCH /v1/counterparties/{id}` (отсрочка контрагента, решение владельца п.2)

Тело `{ "max_deferral_days": 5 }` (целое 0–30, 0 значит «не переносим», по умолчанию у каждого контрагента 0) → `200` и `{ id, name, max_deferral_days }`. `id` это `payments[].counterparty.id`. Ошибки `422` (`fields.max_deferral_days`): `required`, `invalid` (не целое), `out_of_range`; чужой или неизвестный `id`: `404 not_found`. После записи календарь и совет `cash_gap` пересчитываются. Отдельного списка контрагентов (`GET`) в MVP нет: отсрочку задают из разбора платежа в календаре.

#### `GET /v1/obligations?as_of=YYYY-MM-DD`, `POST`, `PATCH /{id}`, `DELETE /{id}`

```json
{ "as_of": "2026-10-07",
  "debt_total": Figure, "monthly_payment": Figure, "monthly_payment_share_pct": Figure,
  "amortization_month": Figure,
  "pnl_month": { "month": "2026-10", "amount": Figure },
  "loans": [ Loan ], "equipment": [ Equipment ] }
```

- `as_of` необязательный (по умолчанию «сегодня»), неверный: `422`. Остатки и месяц `pnl_month` считаются на `as_of`: `remaining` это долг после платежей с датой раньше `as_of`.
- `debt_total` = Σ `remaining` кредитов и лизингов (breakdown по ним, `source = ["manual"]`). `monthly_payment` = Σ `payment` действующих (`status = active`). `amortization_month` = амортизация месяца `as_of` (breakdown по действующему оборудованию, `source = ["calc"]`). `monthly_payment_share_pct` (`pct`): `monthly_payment` к выручке последнего закрытого месяца (breakdown «Платёж в месяц», «Выручка <месяца>»); ключа нет, если выручки нет. Выплаченные (`paid`) и закрытые (`closed`) в итоги, календарь и `pnl_month` не входят.
- **`pnl_month`:** `{ month, amount }` = начисления месяца `as_of` за весь календарный месяц; breakdown «Проценты по кредиту», «Лизинг (платёж целиком)», «Амортизация оборудования». Равно `GET /v1/reports/pnl?month=<тот же>` → `rows[key=obligations].amount` до копейки (gate этапа 4). Основной долг кредита, банковские платежи по кредиту и покупка оборудования в строку не входят.
- **`Loan`** (кредит и лизинг): `{ id, kind: "loan|lease", name, lender|null, principal: Figure, remaining: Figure, paid_pct: Figure(pct), payment: Figure, rate_pct|null, payment_day, next_payment_date|null, last_payment_month: "YYYY-MM", status: "active|paid|closed", closed_from: "YYYY-MM"|null }`. Кредит: аннуитет, проценты месяца = `round(остаток на 1-е число × ставка ÷ 12)` (в `engine/money.py`), последний платёж = остаток + проценты; `paid_pct = (principal − remaining) ÷ principal`. Лизинг: `principal` это сумма всех платежей договора, `remaining` сумма оставшихся (последний платёж может быть меньше), в начисления идёт платёж целиком, предмет лизинга не амортизируется. `principal.breakdown` одна строка «По договору»; `remaining.breakdown` «По договору», «Выплачено» (−), `details` «После платежа <дата>»; `paid_pct.breakdown` «Выплачено», «По договору» (рубли); `payment.breakdown` у кредита «Проценты за <месяц>» + «Основной долг» (сумма равна платежу), у лизинга одна строка. `rate_pct` исключение из общего правила про один знак: число до двух знаков (ввод владельца, не расчёт), у лизинга `null`. `last_payment_month` считает движок. **Статусы:** `active`; `paid` (выплачен, `remaining = 0`); `closed` (закрыт через `DELETE`, `closed_from` = месяц закрытия). Для `paid` и `closed` `remaining.value = 0`, `payment.value = 0`, поэтому тождества `debt_total = Σ remaining` и `monthly_payment = Σ payment действующих` держатся по всему списку; порядок: `active`, затем `paid`, затем `closed`.
- **`Equipment`:** `{ id, kind: "equipment", name, cost: Figure, life_years, in_service_from, amortization_from: "YYYY-MM", amortization_to: "YYYY-MM", monthly: Figure, status: "active|paid|closed", closed_from }`. Линейно, с месяца после ввода, `лет × 12` месяцев, `monthly = round(cost ÷ месяцев)`, последний месяц добирает остаток до стоимости. `monthly`: breakdown одна строка, `details` «Стоимость» и «Срок службы, месяцев» (`count`), `note` с делением; у `paid`/`closed` в `amortization_month` не входит, сам `monthly` остаётся справочным. Оборудование в лизинге не вносится. После последнего месяца `status = paid` («срок вышел»).
- **Тела.** `POST`: кредит `{ kind: "loan", name, lender?, principal, remaining, rate_pct, payment, payment_day }`, лизинг `{ kind: "lease", name, lender?, principal, remaining, payment, payment_day }`, оборудование `{ kind: "equipment", name, cost, in_service_from, life_years }` → `201` и `Loan` или `Equipment`. Деньги целые копейки; `remaining` вводится «на сегодня». `PATCH /{id}`: любое подмножество полей своего вида, `kind` не меняется (другой `kind`: `422`, `fields.kind = "invalid"`), → `200` и объект; правка действует с текущего месяца клиники: перед изменением условий начисления прошлых месяцев записываются в `obligation_charges` (замораживаются), поэтому прошлые отчёты не меняются. Изменение `remaining`, `payment`, `rate_pct`, `payment_day` или `principal` кредита и лизинга строит график заново от остатка «на сегодня» (первый платёж ближайший, не раньше сегодняшнего дня; платёж в выходной идёт в предыдущий рабочий день), `payment_below_interest` проверяется на объединённых значениях. Новый кредит или лизинг начисляется с ближайшего платежа; оборудование амортизируется с месяца после ввода в работу, в том числе за прошлые месяцы. Чужой, неизвестный или закрытый `id`: `404 not_found` (и для `PATCH`, и для `DELETE`).
- **`DELETE /{id}` = «закрыть»** (решение владельца п.4) → `204`: обязательство закрывается с текущего месяца клиники, `status = closed`, `closed_from` = этот месяц (`YYYY-MM`). Платежи календаря и начисления этого и следующих месяцев пропадают, начисления прошлых месяцев остаются в ОПиУ. Объект остаётся в `GET /v1/obligations` (для `as_of` с месяца закрытия), для `as_of` раньше он `active`. Повторное `DELETE`/`PATCH`: `404`. Открыть снова нельзя.
- **Ошибки `422 validation`** (`details.fields`): `kind` (`required`, `invalid`), `name` (`required`, `too_long` > 80), `lender` (`too_long`), денежные поля `principal`, `remaining`, `payment`, `cost` (`required`, `must_be_positive`, `too_large`, `invalid`; `remaining` может быть 0), `rate_pct` (`required`, `out_of_range` 0–100, `too_many_decimals` более двух знаков), `payment_day` (`required`, `out_of_range` 1–31), `life_years` (`required`, `out_of_range` 1–30), `in_service_from` (`required`, `invalid`, `in_future`), `remaining` (`remaining_gt_principal`), `payment` (`payment_below_interest`: платёж не больше процентов месяца; `details.interest` в копейках), `unknown_field` для лишних ключей.

#### `GET /v1/efficiency?month=YYYY-MM&as_of=`

```json
{ "month": "2026-09", "as_of": "2026-10-01", "data_as_of": "2026-10-01T04:12:00+03:00",
  "period": { "month": "2026-09", "status": "closed", "from": "2026-09-01", "to": null, "first_month": "2026-06" },
  "status": "ok|partial|empty", "partial_reasons": [ "no_doctor_hours|no_expenses" ],
  "headline": "Клиника загружена на 21,2%: свободно 544 часа, час работы стоит 461,45 ₽.",
  "load_by": "rooms|doctors",
  "visits": Figure, "load_pct": Figure | null, "avg_check": Figure | null,
  "rooms": [ { "id": "…", "name": "Кабинет терапии", "load_pct": Figure, "busy_hours": Figure, "available_hours": Figure, "free_hours": Figure } ],
  "doctors": [ { "id": "…", "name": "Иванова А.", "visits": Figure, "load_pct": Figure | null, "busy_hours": Figure | null, "available_hours": Figure | null, "free_hours": Figure | null } ],
  "hour_cost": Figure | null, "hour_margin": Figure | null,
  "hour_cost_parts": [ { "key": "hours|busy_hours|fixed|obligations", "label": "Рабочих часов в месяц", "figure": Figure } ] }
```

- `month` необязателен, по умолчанию последний закрытый месяц; формат неверный: `422 fields.month = "invalid"`, месяц позже последнего закрытого: `422 fields.month = "in_future"` (клиент заменяет его на последний закрытый). Часы это `count`; `headline` собирает backend по шаблону (без оценок и рекомендаций); при `status = empty` его нет. Ключи `visits`, `load_pct`, `avg_check`, `rooms`, `doctors`, `hour_cost`, `hour_margin`, `hour_cost_parts` есть всегда (`null` или пустой список, если нет данных).
- **Режим.** `load_by = rooms`, если у каждого кабинета есть расписание и в месяце есть приёмы, привязанные к кабинетам (из Ветменеджера); тогда `doctors = []`. Иначе `load_by = doctors` (запасной режим, основной на старте): `rooms = []`, `doctors[]` заполнен. Один кабинет без расписания переводит весь экран в запасной режим. Ручного ввода кабинетов нет.
- **Часы.** Кабинет: доступно = минуты расписания за месяц ÷ 60 (по календарю, без праздников), занято = сумма длительности его приёмов ÷ 60, оба до целого часа. Врач (запасной режим): доступно = `часов в неделю × дней в месяце ÷ 7`, занято = `приёмов × средняя длительность ÷ 60`, оба до целого часа. `load_pct = Σ занято ÷ Σ доступно` (часы, не среднее процентов). Врач без часов: `load_pct`, `available_hours`, `free_hours` равны `null`, `busy_hours` показан, в итоги не входит (в `load_pct.note`: «Врачей без указанных часов: 1. Они в расчёт не вошли.»); его приёмы входят в `visits`. Нет часов ни у одного врача: `status = partial`, `partial_reasons = ["no_doctor_hours"]`, `load_pct`, `hour_cost`, `hour_margin = null`, `hour_cost_parts = []`.
- `visits` (`count`): приёмы месяца, `breakdown` по врачам и строка «Без врача». `avg_check` (`rub`): выручка месяца ÷ приёмы, `details`: «Выручка за …», «Приёмов». `load_pct` (`pct`): `breakdown` «Занято, ч», «Доступно, ч».
- **`hour_cost`** (`rub`) = (постоянные расходы ОПиУ месяца без статей с признаком `in_service_recipes` + обязательства и амортизация) ÷ доступные часы, одно число на клинику (по кабинетам стоимость не делится). `breakdown` две строки: «Постоянные расходы» и «Обязательства и амортизация» (деньги на час; значение округляется один раз, остаток округления в последней строке). Нет расходов в месяце (нет выписки): `status = partial`, `partial_reasons` содержит `no_expenses`, `hour_cost = null`, загрузка при этом есть. Причины могут идти вместе, в порядке `no_doctor_hours`, `no_expenses`. `status = empty`, если за месяц нет ни приёмов, ни выручки.
- **`hour_margin`** (`rub`) = маржинальная прибыль ОПиУ того же месяца ÷ занятые часы; `details`: «Маржинальная прибыль», «Занятых часов»; `null`, если нет занятых часов или стоимости часа.
- `hour_cost_parts`: четыре строки в порядке `hours` (рабочих часов, в запасном режиме «Часов приёма в месяц»; `breakdown` по кабинетам или врачам), `busy_hours` («Занято»), `fixed` («Постоянные расходы» без статей `in_service_recipes`, `breakdown` по статьям), `obligations` («Обязательства и амортизация», `breakdown` по начислениям). Пуст, пока нет стоимости часа.

#### `GET /v1/efficiency/settings`, `PUT /v1/efficiency/settings`

`{ "avg_visit_minutes": 30, "doctors": [ { "id": "…", "name": "Иванова А.", "hours_per_week": 36.0 | null } ] }` (числа ввода владельца, не `Figure`). `PUT` тело в том же виде (`doctors[].name` не отправляется) → `200` и сохранённое: `avg_visit_minutes` целое 5–240 (обязательно: `required`, `invalid`, `out_of_range`); `doctors` необязателен, врач, которого нет в списке, не меняется; `hours_per_week` число 0–80 с шагом 0,5 или `null` (`out_of_range`, `too_many_decimals` больше одного знака, `invalid` не кратно 0,5); неизвестный или повторный врач: `doctors.N.id = invalid`; врачей клиент не добавляет и не удаляет (они приходят из Ветменеджера).   "started_at": "2026-09-09T04:00:03+03:00", "finished_at": "2026-09-09T04:12:00+03:00" | null,
  "error_code": "invalid_key|unreachable|rate_limited|unknown" | null,
  "counts": { "value": 24, "unit": "count",
              "breakdown": [{ "label": "Новых операций", "value": 21, "unit": "count" }, { "label": "Обновлено", "value": 3, "unit": "count" }],

- Ветменеджер: `connected = true`, когда сохранены адрес и ключ. `key_hint`: последние 4 знака ключа; ключ целиком никогда не возвращается и не пишется в журналы (в базе хранится зашифрованным). `schedule` задан у подключённого Ветменеджера (расписание фиксированное, время в часовом поясе клиники), у банка `null`. `runs`: последние 5 запусков, новые сверху; `last_run` равен первому. `counts`: `value = новых + обновлено`; `null`, если запуск упал до загрузки или ещё идёт. «Пропущено как дубли» в `note` и не входит в `breakdown`, чтобы сумма разбивки равнялась `value`.
- Банк: `connected = true`, если по какому-либо банковскому счёту загружалась выписка. `bank.accounts` это банковские счета клиники (`kind = bank`) с датой последней выписки; у Ветменеджера `bank = null`, у банка `address`, `key_hint`, `schedule`, `last_run` и `runs` пустые.
- `last_success_at`: окончание последнего успешного запуска (Ветменеджер) либо дата загрузки последней выписки (банк).

`PUT /v1/connections/vetmanager`: тело `{ "address": "aibolit.vetmanager.ru", "key": "…" }` (`key` необязателен, если ключ не меняют; при первом подключении обязателен). Сервер проверяет адрес и ключ запросом в Ветменеджер. Адрес принимается только в доменах Ветменеджера (`*.vetmanager.ru`, `*.vetmanager.cloud`, `*.vetmanager2.ru`), схема `https://` и путь отбрасываются. Ошибки `422 validation`: `fields.address = "unreachable"` (адрес недоступен или не из доменов Ветменеджера) и `fields.key = "invalid"` (ключ не принят), `fields.key = "required"` (первое подключение без ключа). Успех: `200` и `Connection`; при первом подключении сразу запускается первая синхронизация (в ответе `last_run.status = running`). Ключ в ответах и логах не появляется.

`POST /v1/connections/{id}/sync`: `202` и `{ "run": SyncRun }` (запуск идёт в фоне, состояние смотрится в `GET /v1/connections`). `409 conflict`, если запуск уже идёт; `429 rate_limited` (с `Retry-After`), если предыдущий запуск начался меньше 5 минут назад; `422 validation` (`details.reason = "not_syncable"`), если подключение не Ветменеджер или не подключено; чужое подключение: `404 not_found`.

`PUT /v1/connections/bank` на этапе 1 не реализуется: банк это загрузка файла (`POST /v1/imports/bank-statement`), интерфейс подключения не использует.

`POST /v1/connections/vetmanager/import` (служебный, для тестов и ручной загрузки без живого Ветменеджера; включён переменной `VETMANAGER_IMPORT_ENABLED=true`, иначе `404`): тело `{ "entities": { "user": {…}, "admission": {…}, "invoice": {…}, "invoiceDocument": {…}, "good": {…}, "payment": {…}, "cassa": {…} } }`, где значение это полный JSON-ответ REST API Ветменеджера по сущности. Обрабатывается так же, как синхронизация; ответ `{ "run": SyncRun }` (запуск завершён). Данные клиентов (`client`, `pet`) не принимаются и не сохраняются.

#### Что загружается из Ветменеджера

Врачи (код `D1`, `D2`… и имя; имя не уходит в ИИ-слой), приёмы (дата, врач), счета (дата, статус, сумма, строки «услуга/товар»; у строки услуги с этапа 5 ещё название, количество и цена единицы, а услуга попадает в справочник `services` с группой), платежи. Кабинеты, расписание и привязка приёмов к кабинетам не загружаются: в REST API Ветменеджера они не подтверждены, поэтому «Эффективность» работает в режиме `doctors`; таблицы `rooms`, `room_schedule_slots`, `room_bookings` и движок готовы к режиму `rooms`. Черновики счетов в выручку не входят, удалённые счета и приёмы отбрасываются. Платежи наличными становятся операциями кассы (`source = vetmanager`, статья «Выручка»); платежи картой операциями не становятся, они идут в сверку эквайринга. ФИО клиентов, телефоны, адреса и свободный текст приёмов не загружаются.
